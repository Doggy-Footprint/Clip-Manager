# File explorer operations review, spec v4

Status: open evidence. Record actual observations, device/build identifiers, screenshots or screen recordings, and input fixture hashes beside each scenario before marking it passed. A blank result is not a pass.

## Fixture and recording protocol

Use disposable shared-storage folders `ExplorerReview/source`, `ExplorerReview/target`, and `ExplorerReview/outside`. Record SHA-256 and byte length of each seed file before the operation. Prepare two files with distinct contents and the same basename in different source folders, a same-name target file, a path-backed media item, and a MediaStore item whose `DATA` path is absent while its content URI opens. Prepare video, image, audio, PDF, TXT and CBZ samples with visible or audible identifying content. Prepare ZIP, CBZ, 7z, tar.xz, tar.gz and tar archives containing a named file with known bytes; encrypted supported archives; malformed and unsupported-method archives; and separate archives with `../outside`, absolute-path and unsafe-link entries. Record the fixture creation command or source and its SHA-256, including the exact archive method. Reinitialize fixtures between scenarios. Capture the app screen and filesystem/URI observations after each step. Never use an irreplaceable file.

For every scenario below, record `device/API`, `build/commit`, `fixture hashes`, `steps completed`, `actual screen/message`, `actual destination bytes`, `actual source bytes`, `artifact paths`, and `pass/fail`. Compare bytes with the seed hashes, not with another output from the app. A visible failure must include the affected item and reason. The app must keep other sources and a readable pre-operation destination state on failure.

## Device matrix: V1, V4, V10; Q3 and Q4

Run the same scenario set on API 24 and API 36, once with a path-backed source and once with a URI-only MediaStore source. Record each of the four API/source combinations separately for Q3. If a device is unavailable, mark its combination open.

1. On each Files, Video, Audio and Images tab, tap an entry in normal mode and record that it opens. Enter Select, tap two visible entries, verify count 2 and bottom Copy, Move, ZIP and Delete actions; toggle one off and verify count 1; clear and verify count 0. Repeat selection and leave for another tab, then return and verify count 0. With no entries, verify selection actions cannot mutate storage. Check item overflow and long press expose operations. Record one capture per tab and the state transitions (V1: select, toggle, clear, leave, empty).
2. Select two files, stage Copy, navigate to `target`, and tap Paste. Compare both destination hashes to seeds. Repeat Move and verify sources disappear only after both destination copies match. With a deliberately inaccessible destination, verify the affected source remains and the failure reason is shown. Record the staged state and Paste control (V2 review supplement).
3. Put same-name files in the destination. For three independent runs, resolve first conflict with a one-item choice, Skip remaining, then Auto rename remaining. Record each prompt and each final name/content to show only Skip and Auto rename persist. In another run cancel a prompt and verify the destination hash and source hash are unchanged and remaining items stay pending. Record dialogs and final listing (V3: per-item, Skip remaining, Auto rename remaining, cancel).
4. Open each of video, image, audio, PDF, TXT and CBZ in the app and capture identifiable displayed or played content. Repeat with a URI-only media entry and record the content URI read. Verify the app does not hand off to another viewer. Record each format separately; the URI-only case is a separate coverage item (V4).
5. For the URI-only item, exercise read, granted write, denied write, granted delete and a stale/missing URI. Record Android consent prompt where applicable, operation outcome, content URI resolution, and source preservation after denial/missing URI. These are five separate decision-table rows (V10). Do not infer URI support from path-backed behavior.
6. Capture six interaction scenarios with asserted state and message: selection and clear, per-item conflict, persisted Skip, persisted Auto rename, password prompt with wrong-password feedback, and destructive delete with trash/restore feedback (Q4). Mark each pass only if the recorded state and message match the spec.

## Archive and trash review: V5–V9

For each of ZIP, CBZ, 7z, tar.xz, tar.gz and tar, browse an archive, record its listed name, extract into an empty destination, and compare extracted bytes to seed SHA-256 (V5). For each format that supports the requested unencrypted edit, independently perform rename, copy, move, delete, paste and creation of a ZIP within an internal directory. Reopen the archive after every operation; record its original container format and entry bytes, names and absence. Inject a pre-replacement write failure using a repeatable test fixture or controlled storage boundary and compare original archive bytes to the seed; record the injection mechanism (V7). Do not count an operation as passed merely because the UI closed.

For encrypted ZIP, CBZ and 7z fixtures separately, enter the correct password and record browse, view and extraction bytes plus read-only controls. Enter the wrong password and record distinct error and unchanged archive hash. Repeat with a corrupt archive and an archive with an unsupported compression method; record distinct reasons and unchanged original hashes, with no partial extraction (V6). For `../`, absolute-path and unsafe-link entries, extract separately and verify there is no file outside the chosen destination, no partial unsafe output and an entry rejection reason (V8). Record the archive fixture's exact entry names and link target.

Delete a regular file and an archive entry. Record the hidden shared-storage trash entry and durable metadata (original location, deletion time, archive origin); verify the trash icon above Settings opens Restore and Empty. Restore the regular file to its original parent and the archived entry as an ordinary file in the archive's parent. Seed a same-name target and verify a unique `_restore` name, matching bytes and no overwritten target. Make the original destination unavailable and verify the trash entry and metadata persist with a reason. Empty and verify removal. For expiration, inject a clock or seed metadata at `7d−1ms`, exactly `7d`, and `7d+1ms` and record retained, expired, expired respectively (V9). Document how time was controlled; wall-clock waiting is not a repeatable procedure.

## Document and code review: V11–V12; Q2 and Q7

V11: input is the `agent-docs/issues/` index and issue file. Record their commit and paths. Observe an indexed entry whose issue states that forced termination during archive replacement lacks recovery and gives a concrete revisit condition. Expected: one indexed issue with both facts. Retain a review note quoting the relevant issue headings and index entry.

V12/Q2: input is the completed implementation at the reviewed commit. Inspect the public UI event handlers and their calls through copy, archive, trash and viewer entry points. For each of these four categories, list the entry point and the executor or dispatcher that performs file, ContentResolver or archive I/O. Expected count of I/O operations directly on the main thread is zero. Record a table of category, entry point, I/O boundary, dispatcher and evidence location. A missing or unknown dispatch path is open, not a pass.

V12/Q7: input is the same commit's local-path, URI and archive operation implementations. Record the public operation contract and the three backend implementations or adapters that conform to it. Expected review count is at least one shared contract across all three. Record signatures and source locations. If archive operations require a separate abstraction, state how they share the public operation semantics and do not silently count unrelated interfaces.
